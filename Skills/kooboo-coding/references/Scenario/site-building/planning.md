# Site Planning Phase (S0–S3)

Read this document only after [Site Building Entry Flow](index.md) has passed. It covers execution readiness through the Design System and contains no site-resource creation steps.

## S0 Execution Readiness Check

Both gates must pass:

- The user explicitly asks to create, build, generate, modify, or continue implementing now;
- For a new site, the business goal and first delivery scope are known; for a modification, the object and expected result are known.

An empty site, an industry description, a capability inquiry, or “do it quickly” alone does not constitute implementation authorization. When conditions are missing, narrow only the largest gap.

## S1 Starting Mode

After S0 passes, use `ask_user_input` to choose:

- P1 Fast Mode: the recommended option; fill in implementation defaults and do not ask item-by-item questions in S2/S3;
- P2 Detailed Mode: converge on key decisions one question at a time.

`buildMode` may only come from this interaction. After receiving a valid value, first use `update_todos` to establish current tasks containing only S2, then begin planning.

## S2 Site Brief and Page Plan

### Current Site Brief Contract

| Field | Constraint |
|---|---|
| `verticalText` | User-readable business description |
| `verticalKeywords` | English industry-search keyword string, space-separated |
| `siteType` | Valid site type matching the current request |
| `tone` | 0–2 items; retain only tones supported by semantic evidence |
| `themeMode` | `light` / `dark` |
| `contentLocale` | `zh` / `en` |
| `pages` | Optional; pass only when the user explicitly specifies the current batch of pages |
| `commerceModel` | Required only for commerce: `catalog-contact` / `online-checkout` |
| `projectName` | Pass when specified by the user; otherwise generated by the script |
| `confirmedCategory` | Leave empty by default; after explicit user confirmation, copy classification.category or a candidate productType, not siteType |
| Design direction | Put natural-language decisions in `creativeDirection` and `palettePreference` |
| `designVariantSeed` | Opaque UUID or script-returned `dvs-*` only; never design prose, industry terms, project names, or placeholders |

The first AI Chat call passes only `mode: "page-plan"` and `brief`, with `brief.designVariantSeed` omitted. AI Chat injects the authoritative session context; outside AI Chat, pass a real top-level `sessionId` or an explicit UUID as top-level `designVariantSeed`. After the Page Plan returns, use `resolvedBrief` as the sole Brief for all subsequent steps.

### Selecting the First Batch of Pages

When `pages` is not supplied explicitly, the script selects an initial set of pages from the complete candidate structure that satisfies the minimum experience loop:

1. One primary entry point;
2. One browsing or core-capability/content-proof path;
3. One evaluation or action loop;
4. Normally no more than 3 pages and approximately 9 page-specific blocks in the first batch; shared Header/Footer are counted separately;
5. Task pages that depend on real business state normally go into a later milestone unless the user explicitly includes them in the current batch;
6. Trust, contact, and detail pages are included based on whether the current site still lacks the corresponding loop.

`pages` is only an explicit batch override. When omitted, the script writes the selected pages to `resolvedBrief.pages`; later batches reuse the same `resolvedBrief` and replace only `pages`.

### URL and Detail-Page Route Contract

Choose the URL shape while planning each independently addressable list/detail experience:

- Use a path parameter for the canonical identity of a detail page. Prefer routes such as `/blog/{slug}` for an article and `/product/{seoName}` for a Commerce product.
- Use query strings for collection state such as search, filters, sorting, and pagination (for example, `/products?category=coffee&page=2`), not for the canonical identity of a detail record when a path parameter can express it.
- Keep the placeholder name stable across the Page `url`, list/detail links, and the detail page's `k-data` binding. A route `/blog/{slug}` is read from the render context as `slug`; `/product/{seoName}` is read as `seoName`.
- Preserve an existing public URL when compatibility is required; otherwise, new detail pages should use the path-first convention and a stable slug/`seoName` rather than a display title or array index.

### P1 / P2 Behavior

- P1: after prerequisites pass, generate the Brief and Page Plan with zero questions; `classification.categoryConfidence` reports the strength of industry evidence. Check the original request first and ask once only if ambiguity changes business content or capabilities. Medium confidence alone does not require a question.
- P2: ask one question at a time to close gaps in goals, audience, scope, content, design, interaction, and dynamic intent; the user must confirm the Page Plan.
- Both modes must briefly show the Brief and Page Plan Summary. Do not write the complete decision process or internal page-role metadata into the conversation.

### S2 Stop Conditions

- Required Brief fields are valid; the Page Plan has returned `resolvedBrief`, pages, and blocks;
- The current batch is deliverable, and the design and content strategy are executable;
- The final commerce intent is explicit through `commerceModel`, without expanding the current batch because of it;
- [Capability Catalog](capability-catalog.md) has been read, and `update_site_milestones` has been called based on the current site's main path.

## S3 Design System

Complete S2 todos first, then switch to S3 todos. After loading `ui-ux-pro-max-pp`, call `mode: "design-system"` with the Page Plan's `resolvedBrief`.

- The output is the authoritative source for site-wide visual variables, layout strategy, and component voice;
- If it includes intent for motion, tabs, accordion, gallery, menu, or similar interactions, read [Motion and Static Interaction](../../Frontend/motion.md) as needed before S4;
- P1 shows the design summary and proceeds directly to S4; P2 waits for user confirmation;
- Before entering S4, complete S3 todos and read [Static Delivery](static-delivery.md).
