# App Base layout delivery

For business Screen imagery and editable images, follow [Images and uploads](../images-and-files.md); reusing a Shell does not imply text-only tables.

This reference owns App Base layout structure. Before installation, read [design-system consumption](../app-design-systems.md); use the selected package guide for Shell parameters. Consume installed layouts directly; follow the read/write steps below when composing or modifying a layout.

## Layouts belong to routes

`app.js` only provides `app.bootstrap` and renders the root `<RouterView />`; it owns no Shell or public/authenticated layout branch. The installer puts the default Shell or temporary skeleton in `layout.default.js`. A parent route references it and its `children` contain business Screens. Multiple layouts use sibling parent routes and separate `layout.<name>.js` components; a standalone top-level Screen needs no layout. Layouts obtain bootstrap through `inject('app.bootstrap')` and keep a child RouterView in their content area. Leaf `meta.public` controls anonymous access independently; do not set `public:true` on layout parents. Navigation includes only pages belonging to the current layout.

Save/read back a new layout before importing it in `router.js`; do not rewrap all pages in the default Shell. Do not key the root RouterView by URL, which would remount the layout on sibling page navigation. For legacy Apps with a Shell in app.js, read the current source, extract its layout, update route children and bootstrap injection, then reduce the root component. Reinstallation does not automatically migrate or overwrite legacy Apps.

## Navigation icons

Follow `references/Frontend/app-design-systems.md` for design-system selection and installation; use the selected package guide for component selection, Shell presets and updates.

When icon choices are known at creation, pass optional `create_app_base.navigationIcons`, mapping exact App Plan Screen IDs referenced by navigation to Lucide kebab-case names, e.g. `{"screen.products":"package"}`. Partial maps are valid: omitted entries produce no `meta.navigationIcon` and can be completed when authoring the Shell. Choose icons from the entry's purpose; the installer writes explicit choices. It validates target IDs and name syntax, not membership in the bundled icon set. Missing-icon behavior follows the selected Shell contract. Without an App Plan, omit the map and set icons when creating business navigation. Existing `router.js` is preserved on repeat installation; edit its route metadata explicitly to change installed icons.

## Complete one visible unit first

1. Establish the intended entry task from the authorized scope and existing source. With an App Plan, select a routed Screen serving that task and preserve an existing entry unless the reviewed requirement changes it. Without planning, implement the current entry task directly; no page inventory is required.
2. Consume the returned shared usage and current component/Shell APIs; read only missing guides. Use props, events, slots, theme tokens and layout contracts rather than reconstructing components from compiled CSS. For Shell padding/scrolling questions, inspect the selected package’s documented adapter stylesheet when needed.
3. When composing or modifying a layout, read installed `layout.default.js` and `app.css`. Preserve bootstrap, RouterView, route protection, account/logout and notifications. Extend the actual setup rather than assuming different Shells expose the same internal state. Group navigation by route metadata; return/register new template variables and handlers or access them through valid Vue instance properties.
4. Write only `/app.css` and `/layout.default.js` changes needed now, then read back those persisted objects. An unchanged runtime Shell needs no rewrite. Preserve Route placeholders until dependencies exist. Check bindings, navigation state, responsive rules and RouterView integration in source.
5. Implement the default Screen's dependency closure (API → service/store → needed components → default Screen), preserving the agreed data strategy. Persist/read back dependencies before replacing only that Route's PlannedScreen. A remaining PlannedScreen means that Screen is unfinished. Integrate the default Screen before starting another Screen.
6. Continue the remaining Screens in the authorized scope one at a time, then reconcile the full scope. Shell completion alone is not business delivery.

## Verification during implementation

Default implementation uses source readback, structural checks, and the limited read-only Preview diagnostics specified in [delivery.md](delivery.md). Continue business implementation after the Shell source checks; browser observations are not a prerequisite for business APIs, mock APIs, service/store modules, or Screens.

Do not initiate browser/iframe observation, element searches or inspection, navigation, clicks, or device switching for layout acceptance during ordinary implementation. Use browser tools only when the user explicitly requests browser testing or operation. Reading component API documentation does not require opening a rendered page.

Report runtime or visual behavior that has not been tested as unverified. Preview unavailability does not block business implementation; retain any outstanding diagnostic evidence requirements without inventing a pass. Repair concrete errors found in source or returned diagnostics, without turning a Shell review into repeated visual tuning.

## Layout rules, not a second design system

- Keep `.app-root` on the application root and `data-app-region="content"` on its primary content container. The base supplies token-driven body typography/colors, zero-specificity button resets, and shrinkable content sizing. It does not supply a sidebar, header, grid, cards, or a fixed scroll model.
- Put `data-app-region="identity"` on the visible App name element. Give the full name or an approved short name enough room; do not squeeze a long name into a narrow sidebar and accept ellipsis. A collapsed mobile rail can hide the name only when it remains readable in the visible header or opened navigation.
- Keep one visible site branding region (name/logo) per view. If the header owns branding, start the sidebar with navigation; if the sidebar owns branding, use the header for the current page or actions. Responsive layouts may relocate branding, but duplicate markup must have mutually exclusive visibility, including when mobile navigation is open.
- Navigation icons are optional. Follow [design-system icon rules](../app-design-systems.md) and the selected package API; do not fill empty slots with placeholders. The creation parameter `navigationIcons` still uses the Lucide-name contract above.
- Every visible navigation, collapse/expand, search, account, and notification control must work. A hamburger must actually open/close navigation at its current breakpoint. Hide it on desktop when collapse is unsupported; otherwise adjust both sidebar and main-area space when toggled. Use semantic buttons, accurate `aria-expanded`/`aria-controls`, and working keyboard/focus behavior. Do not render inert search fields or decorative action controls.
- The account area is a dropdown trigger: clicking the username/avatar opens an account menu with logout inside. Do not render an inert username button beside a separate logout button. Reuse `accountMenuOpen`, `toggleAccountMenu`, and `closeAccountMenu`; bind `aria-expanded` to real state and `aria-controls` to the menu ID. Support trigger toggle, outside-click and Escape dismissal with appropriate focus return, mutual exclusion with notifications, and closing on navigation. If the design package lacks a dropdown, compose semantic controls with its existing panel/list/button and minimal local styling; do not assume a `.dropdown` class exists or omit interaction because a component is absent.
- Before writing, cross-check template and CSS: use actual icons such as `<i data-lucide="menu" aria-hidden="true"></i>` or no icon; remove glyphs such as `☰` and `▦`. Each disclosure needs a handler, real state, target panel, and working visibility rules at the current breakpoint. If `.is-open` only exists inside a mobile media query, hide the desktop trigger. Repeat this source check on readback.
- Reuse the installed `/service.auth.js` for logout, calling `@click="logout()"` or an explicit wrapper so a click event cannot become a URL argument. Real authentication must perform the logout request and session cleanup, then navigate to the login URL supplied by the authentication service. Mock mode must also navigate to login rather than silently returning. Merely closing the account menu, returning to the business homepage, or showing a success message is insufficient; mock navigation does not establish real-session logout.
- Decide where identity, global navigation and account controls belong before writing markup. A separate full-width header containing only right-aligned account controls needs a justified role; move useful existing content into it or integrate those controls elsewhere. Do not add decorative search, help links or metrics to occupy blank space.
- Keep the header to necessary identity/location and a compact action group. Omit slogans restating business scope beside branding; do not give username, logout and notifications equally prominent button styling. Use an appropriate quiet button variant for the account trigger. Page titles and subtitles must convey different information; omit a subtitle that merely repeats `navigationLabel` or the title.
- In the layout phase, write only styles used by the current Shell. Do not prebuild generic `.app-grid-*`, field rows, empty states, drawers or product-option components for future Screens. Account menus and notifications must reuse matching dropdown/popover/list components; an `.app-` prefix and token variables do not justify recreating their backgrounds, borders, radii and typography. If no matching component exists, record that specific gap before adding narrowly scoped styles.
- In `/app.css`, explicitly define the parent grid/flex layout and width allocation. A flex child needs to grow; a grid content track generally needs `minmax(0, 1fr)`. Use App-specific names, for example `.approval-workspace`, rather than assuming an undefined generic `.content` class provides layout.
- The container wrapping `RouterView` owns page insets on all sides, using spacing tokens from the runtime documentation, with desktop and narrow-width treatment. PlannedScreen and real Screens share this padding. Do not add margin to the shared `.app-planned-screen` to conceal missing layout spacing, or duplicate the same outer inset in each Screen. Intentionally edge-to-edge canvases or conversation workspaces need an explicit full-width layout with appropriate internal text/toolbar spacing; missing padding must not accidentally create one.
- Choose a coherent scroll model: normal document scrolling, or a bounded viewport workspace with `min-height: 0` through its flex/grid ancestry and `overflow: auto` on the actual scroll area. Never add `overflow: hidden` to clip content without a reachable scrolling region. Narrow layouts must give navigation an accessible collapse/drawer or stacked presentation; do not leave a full-width desktop sidebar beside a cramped form/table.
- Component classes own typography, backgrounds, borders, radii, shadows, and control sizes. First use an existing component and its supported variants. Do not recreate `.btn`, `.menu-item`, `.table-pagination`, cards, or toolbars in `/app.css`; token-backed replacement visuals are still replacement components.
- If a business composition needs a new container, start with layout-only properties (display, tracks, gap, padding, alignment, sizing, overflow). A new visual surface must reuse the package's card/panel class when available. Add a genuinely missing business visual only after checking the component inventory, with a narrow App-specific selector and existing tokens.
- A narrow responsive override to an existing component must be scoped under an App-specific container and explain the uncovered layout requirement. Do not duplicate unchanged declarations or apply global component overrides.
- Custom semantic controls must retain keyboard, focus and native interaction behavior. Prefer public runtime components; do not modify their internal DOM or treat base resets as a replacement for component contracts.
- Do not add KPI cards, charts, help links, placeholder badges, or secondary navigation just to fill space. Each prominent region must support the default Screen's Blocks/Actions and primary task. Avoid duplicate App identity, page titles, and navigation between Shell and Screen.

## Concrete failure conditions

For an AI-authored layout, initialization is incomplete if `/app.css` is still comments only; an installed runtime Shell may legitimately need no additional App CSS. In either mode, initialization is incomplete if the active route remains PlannedScreen after its business implementation, the App is blank, a template binding is undefined, main content cannot use the available space or scroll, ordinary content accidentally touches layout edges, branding is duplicated, symbols stand in for icons, visible controls do nothing, logout cannot reach login, or the first page contradicts the intended entry task. Repair these conditions before assessing stylistic differentiation or reporting completion.
