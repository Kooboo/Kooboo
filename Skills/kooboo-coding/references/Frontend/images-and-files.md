# Images and file management

Applies to websites, server-rendered Pages/Views, client-rendered Apps and scoped maintenance. Read progressively: display work needs imagery rules; real upload/file maintenance also needs saving and cleanup. Preserve scope, data strategy and static/dynamic stages; add no planning artifacts.

## Business imagery

- Show meaningful image fields for content workflows: product thumbnails, article covers or event posters. Choose image-and-title rows, cards or galleries by task; administration does not imply text-only tables. Do not add decorative imagery to logs or permissions screens.
- Prefer existing assets. When existing or authorized sample records lack imagery, read [ImagePlaceholder](../Functions/image-placeholder.md), compose content-specific in-site URLs and use the same image field in list/detail. Real empty data gets an honest empty state and create action, not invented persisted records. Real storage alone does not justify omitting images from existing sample records.
- Define dimensions/aspect ratio, object-fit, alt text and failure states; use appropriate list sizes. Placeholders are display assets, never downloaded into file storage or included in cleanup.

## Prefer platform thumbnails

In-site image URLs from `k.file` and `k.media` support `?width=320`, `?height=240`, or both dimensions. A single dimension preserves the source aspect ratio. For example: `/__kb/kfile/catalog/photo.jpg?width=320`; append the same parameters to the actual image URL returned by the media library. Use a few fixed sizes for lists/cards and originals or larger sizes for expanded previews. Use CSS object-fit for consistent visual cropping; do not assume these query parameters provide a crop mode. SVGs scale directly rather than using this raster thumbnail path.

Persist the original file identifier and URL; derive thumbnail URLs at display time, preserving existing query parameters and setting width/height correctly. Do not treat thumbnail URLs as separately uploaded assets or add canvas compression, resize endpoints, thumbnail tables or extra physical files for ordinary list thumbnails. Platform thumbnail caching belongs to the platform; business cleanup must not scan its internal cache. Manage only originals and files actually generated by the business feature. Apply this only to supported platform image URLs, not arbitrary external images, placeholder services or private download APIs.

## Default: upload on Save

For ordinary image/attachment forms: select → local preview → Save → upload and bind → success. Multiple product images alone do not justify eager upload. Reuse an existing correct upload implementation rather than rewriting it to match this default.

- Use the existing component's manual upload mode or a native file input, with select, preview, replace, remove and retry; a URL input is not a substitute. Keep Files in the current form, revoke object URLs on replacement/unmount, and never persist base64 bodies or local preview URLs.
- The save flow owns upload state: succeed only after uploads and business save finish; prevent duplicate submits and unhandled navigation while pending. Child upload state must reach the save flow, not merely disable upload controls. Cancel before upload releases local resources without server deletion calls.
- Reuse existing services. When the current API supports it, use one multipart business submission for fields and files. With a separate upload endpoint, await every upload before binding server asset identifiers; retry using still-valid upload results instead of writing duplicates.
- Eager upload is for actual requirements such as rich-text automatic uploads, large/resumable files or cross-session drafts. Then add temporary ownership, TTL, quotas and cancel release. Local image preview alone does not require draft infrastructure, session endpoints or multiple state machines.

## Minimal saving and cleanup contract

For reusable FileIO save, promotion and temporary cleanup primitives, read the optional [FileIO helpers](../../assets/backend-templates/files/README.md). They install no tables or API and do not manage business references. The caller owns the saving/cleanup contract below; static file access remains site-level.

Before writing file APIs, read [request files](../K-Script/core/request.md) and the chosen storage's [k.file](../K-Script/file/index.md) or [k.media](../K-Script/core/media.md) as needed, following [backend conventions](../Backend/index.md). Reuse existing site file management and templates actually present in the capability catalog. Do not assume a generic upload template, automatic tmp cleanup or an unregistered scheduler exists.

1. **Managed storage.** Ownership, storage keys, business references and pending reclamation must be recoverable across requests/restarts. Existing business records, asset tables or upload batches can provide this; a new generic asset platform is not required. Establish recoverable tracking before writing or use an existing reliable staging mechanism, covering partial writes. Prefer one stable storage key and promotion through references/state to avoid orphaning files between rename and metadata update.
2. **Server validation.** Validate count/size, actual file type and permissions. Generate paths on the server; resolve ownership from server records when binding/deleting rather than accepting deletion paths. Private attachments need verified access-controlled storage/downloads. Use confirmed file APIs without speculative decoding/storage fallbacks for imaginary input shapes.
3. **Successful binding.** Coordinate binding and cleanup using transactions/conditional updates supported by the storage; reject expired, reclaimed or unauthorized files. Commit the new reference before releasing the old one; failed saves preserve old files. Delete shared files only without live references. An unprotected check-then-delete must not race a concurrent save that binds the file.
4. **Recoverable failure.** Upload-on-save can still partially succeed or be interrupted; unbound files need expiry/reclamation tracking. Keep retry records when physical deletion fails instead of deleting metadata first. Cancel callbacks provide early release, not the only cleanup for closed tabs or disconnections. Track derivatives, chunks or conversion files only when the feature actually produces them; do not prebuild unused derivative infrastructure.
5. **Real cleanup caller.** Use an existing server scheduler or throttled, bounded request-triggered cleanup, limited to owned files with references rechecked. Repeated failures must not occupy every batch and starve later cleanup. Eager uploads need explicit TTL (normally 24 hours unless specified) and quotas. Request-triggered cleanup promises reclamation on subsequent operations after expiry, never deletion within 24 hours. Absence from a new registry does not authorize deleting legacy media.

Preserve data strategy: mock-only work uses honestly described session previews, never permanent uploads behind fake saves. Real uploads require durable reference/reclamation information. These are outcome requirements, not a checklist of modules or endpoints to create.

## Source readback focus

Trace actual paths for Save during upload, partial upload/business-save failure, replacement preserving old images, cancel/navigation, expiry and deletion retries. Confirm a real cleanup caller, recoverable file tracking on failure and coordination between binding and deletion. Check only implemented capabilities; do not generate sharing, resumable or conversion code for absent requirements. Add no browser acceptance gate and label untested behavior honestly.
