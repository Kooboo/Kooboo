# Kooboo Common Errors Quick Path

This file is the known-error catalog for the [Kooboo Debug SOP](triage.md). It does not replace the general troubleshooting loop; when symptoms and static evidence match a high-confidence rule, it makes AI stop open-ended guessing and immediately perform deterministic checks, a minimal fix, and verification.

## 1. Routing contract

When there is a blank page, HTTP 500, template SSR failure, or a Page / Layout / View rendering failure:

1. Run Preflight during the first evidence pass through `run_skill_script("kooboo-coding", "scripts/preflight-scan.js", ...)`, and read the current Page, bound Layout, and mounted View; do not wait for all Preview tools to recover before running Preflight.
2. Browser Control may reload at most once and wait for a bounded interval; `frame_not_ready`, `agentReady=false`, or unavailable Log / Network is a circuit-breaker signal.
3. If a Preflight finding contains `knownError`, call `read_skill_resource` with `playbook.skillName` and `playbook.resourceName`, then locate this section using `playbook.anchor` and execute the known-error quick path; do not continue generating unsupported parallel hypotheses about ContentType, caching, empty data, and so on.
4. A deterministic rule hit plus direct source evidence in the affected object is enough to confirm this class of root cause; apply the minimal fix when repair is authorized.
5. Rerun Preflight on the same set of objects after the change. When Preview is available, also verify the same route at runtime; when Preview is unavailable, report only `changed_unverified`.

## 2. V1 catalog

| ID | Error | Detection | Current status |
|---|---|---|---|
| `KOOB-CDATA-WRAPPER` | Page / Layout / View body wrapped in XML CDATA | `PF-UNIVERSAL-004` | Integrated into quick path |
| `KOOB-LAYOUT-PAGE-ASSEMBLY` | Layout / Page / View or placeholder assembly error | `PF-KOBOO-TEMPLATE-003/005/007/010/013/014` | Integrated into quick path |
| `KOOB-KDATA-STRUCTURE` | `k-data` query, export, branch, scope, or binding structure error | `PF-KOBOO-TEMPLATE-006/011/012/015/016/017` | Integrated into quick path |
| `KOOB-RESOURCE-REFERENCE` | Script / Style / Image / View or other resource reference failure | `PF-KOBOO-RESOURCE-001/002` + Network | Integrated into quick path |
| `KOOB-AUTH-HEADER-STALE` | Header not updated after successful login | Login replay + Network + state-source inspection | Pending |

Only entries marked “Integrated into quick path” are guaranteed to make Preflight return a structured `knownError` route. Do not describe “Pending” entries as automatically detected.

## 3. `KOOB-CDATA-WRAPPER`

### 3.1 Typical signals

- The page is blank, returns 500, or the Page / Layout / View does not render at all.
- The object body returned by `read_object_text` starts with `<![CDATA[` and usually ends with `]]>`.
- Preflight returns `PF-UNIVERSAL-004` with:

```json
{
  "knownError": {
    "id": "KOOB-CDATA-WRAPPER",
    "priority": "immediate",
    "playbook": {
      "skillName": "debug",
      "resourceName": "references/common-errors.md",
      "anchor": "3-koob-cdata-wrapper"
    }
  }
}
```

### 3.2 Root cause

`create_page`, `create_layout`, `create_view`, and `update_text_object` pass the body through JSON and do not require XML CDATA escaping. Wrapping complete HTML in `<![CDATA[...]]>` writes the XML wrapper into the Kooboo object body and breaks template parsing or rendering.

Keep the detection rule model-independent. Even if the problem is more common with content generated by one model, rely on post-save Preflight rather than only on the model prompt.

### 3.3 Confirmation steps

1. Identify the Page, bound Layout, and mounted View for the current route.
2. Run Preflight on these objects.
3. Read the real object bodies for every `PF-UNIVERSAL-004` hit.
4. Confirm that CDATA is an outer wrapper around the object body, or that it was actually written as erroneous template text; do not modify based only on the user's report of a blank page.
5. Record the complete affected-object list so that a same-source wrapper in Layout / View is not missed while fixing only the Page.

The Preflight finding plus `<![CDATA[` in the body is sufficient direct evidence; do not continue waiting for the iframe to confirm this static root cause.

### 3.4 Minimal fix

When write authorization such as “diagnose and fix” is present:

1. For a complete outer CDATA wrapper, remove only the opening `<![CDATA[` and matching closing `]]>`; preserve the inner HTML exactly.
2. If CDATA occurs in the middle of the body or in multiple segments, inspect the context first; do not perform a global string replacement that could delete valid characters in Script / SVG or text.
3. Save the pure HTML body with `update_text_object`.
4. Do not also refactor the template, data query, visual styles, or Layout structure.
5. Rerun Preflight on the same Page / Layout / View set.

### 3.5 Verification and result status

Minimum static verification:

- `PF-UNIVERSAL-004` no longer appears for the same set of objects.
- This Preflight run has no other `BLOCKER`.
- Read the object bodies back and confirm that no outer CDATA remains and the inner HTML was not truncated.

Full runtime verification:

- Reload the original route.
- Confirm that the page actually renders.
- Confirm that the original 500 / blank page no longer occurs.
- Confirm that Runtime Log and Network have no related new errors.

Result wording:

- Static and runtime both pass: `fixed_verified`.
- Static passes but Preview remains unavailable: `changed_unverified`; state the missing runtime verification in remaining risks.
- The user authorized analysis only: `diagnosed`.
- The object cannot be read or there is no write permission: `blocked`.

### 3.6 Prohibited actions

- After `PF-UNIVERSAL-004` is hit, do not repeatedly call Browser Control while waiting for the same iframe.
- Do not hide the rule hit with comments, HTML entities, or another CDATA wrapper.
- Do not claim that the whole page is restored after fixing only the first object.
- Do not claim that the BLOCKER is cleared without rerunning Preflight.
- Do not skip deterministic post-save scanning because CDATA is frequent with one model.

## 5. `KOOB-LAYOUT-PAGE-ASSEMBLY`

This class covers cases where the objects exist but the responsibilities or references among Layout, Page, placeholder, and View do not close correctly. It differs from “the referenced View / Script / Style does not exist at all”; the latter belongs to `KOOB-RESOURCE-REFERENCE`.

### 5.1 Correct assembly contract

A Page with a Layout must satisfy all of the following:

1. The Page `layoutName` points to a real, readable Layout.
2. Page content uses `<layout id="LayoutName">...</layout>` as the outer container, with `id` matching `layoutName` and the Layout object name.
3. The Layout declares injection areas with attributes such as `k-placeholder="Main"`.
4. The Page provides content inside `<layout>` using `<placeholder id="Main">...</placeholder>`.
5. The Page placeholder id exactly matches the Layout `k-placeholder` value, including case.
6. Site-wide chrome Views such as Header / Footer are referenced by the Layout by default; page-level Views such as Hero and Features are orchestrated by Page placeholders only.
7. A View contains reusable blocks only; it does not wrap `<layout>`, `<placeholder>`, a complete `<html>`, or duplicated site-wide chrome.

Minimal correct structure:

```html
<!-- Layout: main -->
<body>
  <view id="site_header"></view>
  <main k-placeholder="Main"></main>
  <view id="site_footer"></view>
</body>
```

```html
<!-- Page: home, layoutName=main -->
<layout id="main">
  <placeholder id="Main">
    <view id="home_hero"></view>
    <view id="home_features"></view>
  </placeholder>
</layout>
```

### 5.2 Rules and meaning

| Rule | Confirmed problem |
|---|---|
| `PF-KOBOO-TEMPLATE-003` | The Page declares `layoutName` but lacks a correct `<layout id>` or `<placeholder>`, or `<layout id>` differs from `layoutName` |
| `PF-KOBOO-TEMPLATE-005` | The Layout has no `k-placeholder` and cannot carry Page content |
| `PF-KOBOO-TEMPLATE-007` | The Layout and Page placeholder reference the same View twice, usually causing duplicate Header / Footer |
| `PF-KOBOO-TEMPLATE-010` | The Page `<placeholder>` is outside `<layout>`, or `<layout>` is empty-closed |
| `PF-KOBOO-TEMPLATE-013` | The Page placeholder id has no same-named `k-placeholder` in the Layout, including a case mismatch |
| `PF-KOBOO-TEMPLATE-014` | The Page `layoutName` points to a Layout that does not exist or cannot be read |

When these rules hit, route to:

```json
{
  "knownError": {
    "id": "KOOB-LAYOUT-PAGE-ASSEMBLY",
    "priority": "immediate",
    "playbook": {
      "skillName": "debug",
      "resourceName": "references/common-errors.md",
      "anchor": "5-koob-layout-page-assembly"
    }
  }
}
```

### 5.3 Confirmation steps

1. Read the current Page's real `layoutName` and body; do not infer the Layout from the route name alone.
2. Read the Layout body and include the Page and Layout as artifacts in the same Preflight; the Page artifact must carry `layoutName`.
3. List all `k-placeholder` values in the Layout and all `<placeholder id>` values in the Page, matching them one by one with their original case.
4. List the Views referenced by the Layout and Page placeholders and check whether a same-named View is owned by both.
5. Determine the responsibility of duplicate Views: site-wide chrome stays in the Layout by default; page-level blocks stay in the Page by default.
6. If a `<view id>` points to a missing object, do not guess creation content in this playbook; switch to `KOOB-RESOURCE-REFERENCE`.

When Preflight has returned a deterministic finding, repeated Preview refreshes are not needed to confirm tag nesting or a name mismatch.

### 5.4 Rule-specific minimal fixes

#### `003`: incomplete or inconsistent Layout binding

- Use the Page's actual `layoutName` and the real Layout object name as authoritative.
- Correct the Page outer `<layout id>` and complete the nested `<placeholder>`.
- Do not rename the Layout at the same time unless the user explicitly requests renaming.

#### `005`: Layout lacks an injection area

- Add `k-placeholder="..."` at the actual page-body location in the Layout.
- Do not mechanically append it to the end of `<body>`; the injection position must fit the page skeleton.
- Then make the Page use exactly the same placeholder name.

#### `007`: duplicate View reference

- Keep shared Views such as Header / Footer, site-wide navigation, and global notices in the Layout by default; remove duplicate references from the Page placeholder.
- Keep page-specific Views in the Page by default; remove them from the Layout only when they were mistakenly included there.
- Do not hide one copy with CSS.

#### `010`: placeholder is outside layout

- Move `<placeholder>` inside the corresponding `<layout>`.
- Delete empty-closed `<layout></layout>` and parallel structures; do not duplicate placeholder content.

#### `013`: placeholder name mismatch

- By default, correct the Page `<placeholder id>` to match the Layout `k-placeholder`.
- Modify the Layout only when its area naming is genuinely wrong and affects multiple Pages, and then check every bound Page.
- Name case must match exactly.

#### `014`: Layout does not exist or cannot be read

- First determine whether this is a name error, an object that has not been created, or a read-permission problem.
- For a name error, correct the Page `layoutName` and `<layout id>`.
- Do not create an empty Layout with the same name just to make Preflight pass; create a complete skeleton only when the requirement truly needs a new Layout.

### 5.5 Verification

Static verification must include:

- Rerun the same Preflight on the Page, bound Layout, and involved Views.
- `003/005/007/010/013/014` no longer appear.
- Page `layoutName`, `<layout id>`, and the real Layout name match.
- Page placeholders correspond one-to-one with Layout `k-placeholder` values and match case.
- Shared Views and page-level Views are not owned by both sides.

Runtime verification must at least check:

- The original route actually renders.
- Header / Footer appear only once.
- The Page body enters the correct placeholder.
- Page-level View order is correct and no View is missing.
- Preview Log has no new template errors and Network has no related resource failures.

Report `changed_unverified` when static checks pass but Preview is unavailable. Report `fixed_verified` only when the actual page assembly and key Views display correctly.

### 5.6 Prohibited actions

- Do not modify only Page content while forgetting to pass or preserve the correct `layoutName`.
- Do not treat `<layout>` as the same declaration tag as `<view>`; it must wrap `<placeholder>`.
- Do not lowercase all Page placeholder names; placeholder matching is case-sensitive.
- Do not reference Header / Footer in both Layout and Page and then hide duplicates with styles.
- Do not create an empty Layout directly when the Layout cannot be read.
- Do not mistake a missing View reference for a placeholder assembly error; switch to the resource-reference quick path.

## 6. `KOOB-KDATA-STRUCTURE`

Many KData errors do not produce a clear exception; they silently “do not generate a variable” or “do not expose it to the template”, so they are often mistaken for an empty database, endpoint failure, or a broken `k-for`. Debug must rule out the structural contract before investigating real data.

### 6.1 Key runtime contract

- DataEvaluator parses only the inner HTML of `<k-data>`; `query` and other tags placed outside do not enter the KData flow.
- A `query` with no non-empty `as` ends immediately and writes no variable.
- If `source` / `action` cannot find a registered query, execution ends immediately and writes no variable.
- `export` is a Boolean attribute of `query` / `let`; no value or `true` exposes the value, while `false` or omission does not.
- Only values actually generated and exposed by the current `query` / `let` `export` attribute enter the template DataContext.

Therefore, “the template variable is empty” has at least three distinct causes: the query did not execute, the query executed without declaring `export`, or the query executed and declared `export` but the real result is empty. Distinguish them in this order.

### 6.2 Rules and meaning

| Rule | Confirmed problem |
|---|---|
| `PF-KOBOO-TEMPLATE-006` | `k-attribute` interpolation performs arithmetic directly; precompute it in KData through `let use` |
| `PF-KOBOO-TEMPLATE-011` | `<query ... />` is self-closing and may swallow later KData nodes |
| `PF-KOBOO-TEMPLATE-012` | `when` / `else-if` / `else` is written outside KData |
| `PF-KOBOO-TEMPLATE-015` | query lacks `as/source/resource/action`, or uses an unsupported source/action |
| `PF-KOBOO-TEMPLATE-016` | `query` / `let` `export` lacks `as`, or uses an invalid Boolean value |
| `PF-KOBOO-TEMPLATE-017` | query/try/catch/redirect is outside `<k-data>` |

Structured route:

```json
{
  "knownError": {
    "id": "KOOB-KDATA-STRUCTURE",
    "priority": "immediate",
    "playbook": {
      "skillName": "debug",
      "resourceName": "references/common-errors.md",
      "anchor": "6-koob-kdata-structure"
    }
  }
}
```

### 6.3 Confirmation order

1. Read the real Page / Layout / View bodies containing KData and run Preflight.
2. Fix every deterministic `006/011/012/015/016/017` finding first; do not change database query conditions first.
3. Map the variable chain:

```text
let/query 的 as
→ 后续 from / where / page-number / page-size 引用
→ 当前标签的 export 属性
→ 模板层 k-for / k-content / k-attribute
```

4. Confirm that names match character-for-character, especially query/let `as`, map `from`, and template variables.
5. Only after the static structure passes, check whether source/resource/action matches the [Query Reference](../../kooboo-coding/references/Frontend/k-data/query.md), along with real data, filters, permissions, and request parameters.

Do not read the array from `action="list"` as a single object. When a unique identifier is known and details are needed, change to `action="item"`; use `<let from="products[0]" as="product"></let>` only when the business meaning is truly “the first item in an ordered result”. Lists from paged queries are usually read from `result.list`; do not guess `items` from experience with another framework.

### 6.4 Minimal correct example

```html
<k-data>
  <query export
    as="products"
    source="commerce"
    resource="product"
    action="list"
  ></query>
</k-data>

<div>
  <article k-for="product in products">
    <h3 k-content="product.title"></h3>
  </article>
</div>
```

### 6.5 Rule-specific minimal fixes

- `006`: Precompute with `<let use="add|subtract|multiply|divide|modulo">`; the template binds only the result variable.
- `011`: Change query to an explicit `</query>` and check whether later nodes were incorrectly nested.
- `012`: Move data-flow branches into `<k-data>`; use `k-if/k-else-if/k-else` for template DOM branches.
- `015`: Complete the four core query attributes; correct source/action according to the Query reference instead of trying spelling approximations.
- `016`: Put `export` on the `query` / `let` whose result must be exposed and ensure the tag has a non-empty `as`; Boolean values may only be no value, `true`, or `false`.
- `017`: Move KData elements into the same `<k-data>` container while preserving execution order and variable dependencies.

Fix only the structural problems that were hit, one at a time. If data is still missing after the structure passes, investigate Network, server logs, real data, and conditional expressions.

### 6.6 Verification

Static verification:

- Rerun Preflight on the affected objects; `006/011/012/015/016/017` no longer appear.
- Every query has valid `as/source/resource/action`.
- Every query/let with `export` has a non-empty `as` and a valid Boolean value.
- Query and control-flow tags are inside `<k-data>`.
- Template-consumed variable names exactly match the `as` of tags with `export`.

Runtime verification must cover at least:

- No matching data: the page shows the correct empty state instead of losing structure because a variable is undefined.
- One record: field bindings are correct.
- Multiple or paged data: list count, pagination fields, and ordering match the real result.
- After request parameters change, the corresponding `let` for queryString/path/form and the query result change together.
- Preview Log, Network, and server logs have no related errors.

Report `fixed_verified` only after observing the real data path and expected UI. Report `changed_unverified` when the static structure passes but data or Preview cannot be accessed.

### 6.7 Prohibited actions

- Do not rewrite KData as `<script env="server">` plus a guessed `k.*` API just because data is empty.
- Do not write `export` as a standalone tag or add an `export` attribute unsupported by the current runtime to `map`.
- Do not hide an unexecuted query by adding default fake data to every variable.
- Do not mix the return shapes of list, paged, and item.
- Do not modify where, permissions, or database content before structural findings are cleared.

## 7. `KOOB-RESOURCE-REFERENCE`

This class contains two subproblems with different evidence strength:

1. **Referenced View does not exist**: Page / Layout / View source and the site View list can establish this, so it is an immediately actionable static root cause.
2. **Local Script / Style / Image / CmsFile URL is missing or wrong**: Preflight can confirm that the reference does not match a real Route for a current site object, but a failed Preview Network request is still needed to confirm runtime impact.

Do not classify every “View is not displayed” issue here. If the View object exists but is in the wrong Layout, Page, or placeholder, switch to `KOOB-LAYOUT-PAGE-ASSEMBLY`.

### 7.1 Key runtime contract

- In a normal site template, `<view id="...">` resolves by View name or ID; when the object is missing, the renderer records a View 404 and outputs empty content.
- Style, Script, Image, and CmsFile are exposed through site Route URLs; HTML / CSS should reference the real `Url` returned by the object list.
- In-site object URLs should use root-absolute form, such as `/app.css`, `/main.js`, and `/images/hero.webp`, so the current Page route cannot change relative-URL resolution.
- External `https://...`, protocol-relative URLs, `data:` / `blob:`, dynamic template values, and system or API addresses such as `/_api/` are outside this static Route rule.

### 7.2 Rules and meaning

| Rule | Severity | Confirmed problem |
|---|---|---|
| `PF-KOBOO-RESOURCE-001` | `BLOCKER` | `<view id>` does not exist in the site View name/ID list; routes immediately to this playbook |
| `PF-KOBOO-RESOURCE-002` | `HIGH` | `<script src>`, stylesheet `<link href>`, media `src/srcset/poster`, or CSS `url()` uses a relative URL or has no matching real Route for Script / Style / Image / CmsFile |

The structured route priority for a missing View is `immediate`:

```json
{
  "knownError": {
    "id": "KOOB-RESOURCE-REFERENCE",
    "priority": "immediate",
    "playbook": {
      "skillName": "debug",
      "resourceName": "references/common-errors.md",
      "anchor": "7-koob-resource-reference"
    }
  }
}
```

When only a local static URL is hit, the priority is `normal`. AI should read the corresponding Network record first instead of modifying an object based directly on the file extension.

### 7.3 Confirmation order

1. Run Preflight on the current Page, bound Layout, and mounted View; do not scan only the one object last mentioned by the user.
2. When `001` hits, call `list_site_object` for the View list and confirm by name or ID that the reference truly does not exist.
3. Distinguish a name typo, a reference to a deleted object, and an object that has not been created; do not misclassify it as a placeholder assembly error.
4. When `002` hits, read Preview Network in issues mode and find a failed, timed-out, or abnormal request for the same URL.
5. Read the real `Url` returned by `list_site_object(Style|Script|Image|CmsFile)` separately and check:
   - whether the reference incorrectly adds imagined directories such as `/src/js/`, `/src/css/`, or `/assets/<project>/`;
   - whether it uses a relative URL that changes with the Page route;
   - whether the same-named object is actually published at another Route;
   - whether the request URL still maps to the same resource Route after query/hash processing.
6. If the Network request succeeds, or the failed URL is an API, external CDN, or dynamic template value, do not modify it under `002`; switch to the relevant Network, CSP, authentication, or external-dependency investigation.

The `001` Preflight finding plus the View list is sufficient static root-cause evidence. A `002` hit alone only means “the current reference does not match the site resource list”; the complete root cause still needs failed Network evidence or the real Route of the same-named object.

### 7.4 Minimal fix

#### View does not exist

- If it is only a spelling or case difference, correct `<view id>` to the real name of the existing View.
- If the View was renamed, update the reference; do not copy the old View or create a compatibility shell.
- If the requirement genuinely lacks the block, first determine whether it is shared chrome or a page-level block, then create a View with complete responsibility and content and place it in the correct Layout or Page.
- Do not create an empty same-named View just to make Preflight pass.

#### Incorrect local resource URL

- Use the real `Url` returned by the object list and write it as a root-absolute URL.
- Modify only the erroneous `src` / `href` / `srcset` / `poster` / CSS `url()`; do not also rename resources or change directory structure.
- If the reference is `/src/js/main.js` but the Script's actual URL is `/main.js`, change the reference to `/main.js`; do not create another `/src/js/main.js`.
- If the real object itself lacks the expected Route, first confirm its creation parameters and route configuration, then decide whether to correct the object; do not keep guessing paths in the template.

### 7.5 Verification

Static verification:

- Rerun Preflight on the original Page / Layout / View / Style.
- `PF-KOBOO-RESOURCE-001/002` no longer appear.
- Every `<view id>` can be found in the View list.
- Every in-site static URL matches the real Route of its corresponding object and uses root-absolute form.

Runtime verification:

- Reload the original route and replay the original actions.
- The missing View's actual content and position appear correctly instead of merely removing a 404.
- The original Script / Style / Image requests return success status.
- Console no longer contains resource-loading or script-parsing errors.
- Network has no duplicate requests, redirect loop, or wrong MIME type introduced by the path correction.

Report `fixed_verified` only when both static checks and runtime resource loading pass. If Preview is unavailable or `002` has no readable Network evidence, report `changed_unverified` or `diagnosed` and state the missing verification evidence.

### 7.6 Prohibited actions

- Do not create an empty same-named View just because `<view id>` is not displayed.
- Do not treat a Layout / Page assembly error as a missing resource.
- Do not guess `/css/`, `/js/`, or `/assets/` prefixes because a URL looks like a file path.
- Do not modify external CDN, API, or dynamic-template URLs to satisfy the site-object Route list.
- Do not claim a confirmed 404 from a Preflight `002` alone; read Network or find the real Route of the same-named object.
- Do not verify only the HTTP status; for Script / Style also confirm MIME, execution, and that styles actually take effect.
