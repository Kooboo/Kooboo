# 前端交互指南

适用于公开站点、会员中心、商城及 ToB App 的页面与组件，不依赖框架、渲染方式或设计系统。规划页面交互、编写或修改前端交互代码前必须读取；本会话已完整读取且内容未变时无需重复读取。

本文规定任务入口、编辑容器、状态反馈和退出行为。[前端代码风格](code-style.md) 负责代码写法，[前端视觉设计](frontend-design.md) 负责视觉表达。所选设计系统负责组件外观，不能取消本文要求的操作边界。仅调整颜色、间距等且不改变交互的局部任务，不因此扩大为流程重构。

## 1. 按任务复杂度选择编辑容器

| 任务 | 使用方式 | 选择依据 |
|---|---|---|
| 新增或修改少量独立字段，如名称、备注、分类 | 模态弹窗 | 一个明确目标、短表单、一次提交，无复杂关联或子表 |
| 多分组表单、关联对象、子表明细、复杂校验、多步骤操作 | 独立详情／编辑页 | 需要足够空间和稳定上下文，可能长时间操作 |
| 快速查看摘要、辅助信息 | 只读弹窗或抽屉 | 看完继续当前任务；提供完整详情入口 |
| 完整详情、需要分享或刷新后恢复的内容 | 有独立 URL 的详情页 | 支持直接访问、刷新、浏览器前进和后退 |
| 删除、发布、作废等需要确认的操作 | 站内确认弹窗 | 明确对象、影响及最终动作 |

- 简单编辑必须用弹窗，复杂编辑必须用独立页面；不要将抽屉当作通用编辑容器。
- 复杂度以操作关系、校验和工作量判断，不只数输入框。BOM 即使基本字段少，只要涉及组分、用量、损耗及版本维护，就属于复杂编辑。
- 新增和编辑同类对象使用一致的容器与字段组织。复杂新增也应进入独立页面。
- 详情页和编辑页可以共享组件，但必须有明确的查看／编辑状态、可恢复的路由及保存／取消边界。

## 2. 禁止用局部显隐拼接编辑流程

- 禁止点击新增／编辑后，在列表右侧、下方或行内通过 `v-if`、`v-show`、CSS 显隐等突然展开编辑表单；禁止用几个布尔变量在同一区域切换列表、完整详情和编辑来代替路由。
- 不使用常驻的“新建对象”侧卡占据列表空间。未开始新增时不要显示半成品表单或无对象的编辑面板。
- 列表负责检索、比较、选择和操作入口。只读预览可以采用明确的主从布局；进入编辑仍遵循上一节，不把预览卡原地变成表单。
- `v-if` 等可正常用于弹窗挂载、加载状态、权限展示、条件字段及只读区域；限制的是交互模式，而非模板语法。
- 复杂编辑页内的明细表可以提供增删行和单元格输入，但属于同一个明确的编辑会话，有统一保存／取消，不等同于在检索列表中展开编辑。

例如 BOM 列表：“新建 BOM”进入独立新建页，“查看明细”进入详情页，“编辑明细”进入包含基础信息、组分表和校验反馈的编辑页；仅修改备注时使用弹窗。不要在列表右边展开一张“新 BOM”卡片，再在卡片中逐步补齐复杂编辑。

## 3. 使用站内反馈组件

禁止调用浏览器原生 `alert()`、`prompt()`、`confirm()`（包括 `window.*` 形式及封装后的间接调用）承载业务交互。使用与当前设计系统一致的弹窗、消息、通知和表单组件。

| 情况 | 反馈方式 |
|---|---|
| 普通保存成功 | 简短、非阻塞的轻提示，并更新对应内容 |
| 字段校验失败 | 字段旁显示具体原因和修正要求，定位首个错误 |
| 表单提交失败 | 在表单内保留错误和已填内容，允许修正或重试 |
| 页面加载失败 | 明确错误状态与重试入口，不展示成空数据 |
| 长任务或批量操作 | 显示进行中状态、进度（可获取时）和最终结果；区分部分成功与全部成功 |
| 需要用户决策 | 站内确认弹窗，提供明确选项 |

不要用转瞬即逝的轻提示作为重要错误的唯一载体，不要用成功弹窗要求用户重复确认普通保存。提示使用业务语言，不把内部异常堆栈直接展示给用户。

## 4. 编辑、保存和退出形成完整闭环

- 打开表单时编辑独立副本；取消或关闭不能修改列表、详情中的已保存数据。再次打开时按目标对象重新初始化，不能残留上一次的值或错误。
- 提交前校验必填项、格式和跨字段规则。前端校验帮助操作，服务端仍负责权威校验和权限检查。
- 提交期间展示忙碌状态并阻止重复提交。只有收到成功响应后，才报告成功、退出编辑并按数据契约更新界面；失败保留输入。
- 有未保存修改时，关闭按钮、取消、遮罩、Esc、应用内跳转或返回必须经过一致的放弃修改处理；无修改时直接退出。保存进行中不得通过关闭造成结果含糊不清。
- 应用内离开提示使用站内确认组件。只有确需防止浏览器刷新／关闭丢失输入时，才可在有未保存修改期间使用 `beforeunload` 的浏览器离开保护；它不是业务弹框替代品，不能依赖自定义提示文案。
- 自动保存只用于明确设计为自动保存的流程，显示保存中、已保存、失败状态，提供适当的恢复能力；不能把普通表单悄悄改成输入即持久化。
- mock／静态交付遵守当前数据策略：不伪称已持久化，不为了满足交互示例提前接入真实提交、API 或存储。未接入的动作明确说明当前可用范围。

## 5. 列表、详情与导航保留上下文

- 从详情／编辑返回列表时保留搜索词、筛选、排序、页码，并尽可能恢复滚动位置。保存后更新相应记录；删除最后一条记录后合理回到有效页。
- 详情和复杂编辑使用稳定 URL 及对象标识，支持直接打开和刷新。对象不存在、无权限和加载失败分别提供明确状态及返回入口。
- 搜索或筛选变化时回到适合的起始页；异步请求必须避免旧响应覆盖新条件的结果。显示当前筛选，并提供清除入口。
- 区分首次无数据、无匹配结果、加载中、加载失败：分别提供合适的新增、清除筛选、等待或重试反馈。
- 行操作只影响对应记录，不能同时触发行导航。批量操作显示选择数量和范围，筛选或翻页后不得悄悄改变操作对象。

## 6. 操作层级、危险操作与业务状态

- 每个操作区域突出一个主要动作。页面级新增放在工具栏，单条操作放在记录上，批量操作在有选择时呈现；不要在页面多处重复同一个主按钮。
- 按钮写清动作和对象，例如“保存修改”“删除订单”“确认作废”；确认弹窗避免只写“确定”。取消作为明确的次要操作。
- 删除、作废、覆盖等危险操作的确认须说明对象、影响范围及可否恢复。普通保存不增加无意义的二次确认；不可恢复且影响大的操作可按风险要求再次核对对象。
- “保存草稿”与“发布／生效／提交审批”明确区分，保存不能隐式推进业务状态。状态转换遵循业务规则，不为了按钮可用而绕过前置条件。
- 不可用操作提供原因；无权限的操作按产品策略隐藏或禁用，但前端显隐不能替代服务端授权。按钮不能点击后无反馈。

## 7. 弹窗、表单与响应式可访问性

- 弹窗有可感知的标题、关闭入口及正确的对话框语义；打开时移入焦点，焦点保持在模态内，关闭后返回触发控件或合理的后续位置。
- 支持键盘操作和可见焦点，Esc 与其他退出入口遵循同一未保存规则。避免层层嵌套弹窗；复杂任务改用页面。
- 表单使用持久标签，不以 placeholder 代替标签；说明单位、必填和格式。错误关联到字段，状态不能只靠颜色表达；非提交按钮明确使用 `type="button"`。
- 小屏可将简单编辑弹窗调整为全屏模态，复杂编辑仍保留独立页面。合理安排滚动，确保标题、关闭和保存操作可到达，不能被软键盘或固定栏遮挡。
- 不把桌面左右分栏硬塞进窄屏；行操作不能只在 hover 时出现，图标按钮提供可访问名称，工具提示不能作为唯一说明。

## 8. 在规划与实施中落实

- 站点：在 Page Plan 的既有页面／交互描述中写明入口、容器、保存／取消及成功／失败行为；静态阶段明确演示边界，动态化时沿用交互契约。
- App：在既有 Screen／Action 中表达规则。简单编辑的 `presentation.desktop` 使用 `modal`，移动端按需要用 `modal` 或 `fullscreen`；复杂编辑使用 `page` 并指定 `targetScreenId`。枚举支持 `drawer`、`split-pane`、`inline` 不代表它们适合编辑。
- 新建或调整交互时，在编码前按本文选定方式。已有计划与规则冲突时，按原工作流修正相关交互契约后实施，不在代码里悄悄替换计划，也不为纯样式修改重建规划。
- 不新增平行的规划 Artifact 或扩展 Schema 来保存这些约定，使用既有描述、反馈及验收字段。

审阅时围绕实际操作检查：入口是否明确；容器是否匹配复杂度；取消是否无副作用；失败是否保留输入；返回是否保留上下文；危险操作是否说明后果；键盘和小屏是否能完成相同任务。运行验证仍遵守用户授权与当前交付阶段，不因本文自动扩大测试或构建范围。
