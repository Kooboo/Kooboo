# App Base 布局交付

业务 Screen 的配图与可编辑图片遵循 [图片与上传](../images-and-files.md)；复用 Shell 不代表主区只能生成文字表格。

本文定义 App Base 的布局结构。安装前读取 [设计系统消费规则](../app-design-systems.md)；具体 Shell 参数遵循所选包指南。已安装布局直接消费；自行组合或修改布局时执行下文读写步骤。

## 路由拥有布局

`app.js` 只提供 `app.bootstrap` 上下文并渲染根 `<RouterView />`，不放 Shell、不按公开/登录状态分支。安装器把默认 Shell 或临时骨架写入 `layout.default.js`，路由父级引用它，业务页面放在其 `children` 中。多个布局使用同级父路由和独立的 `layout.<name>.js`；不需要布局的页面直接作为顶层路由。布局组件通过 `inject('app.bootstrap')` 取启动数据，并在内容区保留子级 RouterView。公开访问仍由页面的 `meta.public` 决定，与布局选择无关；不要在布局父级统一设置 `public:true`。导航只收集当前布局下的页面。

新增布局前先保存并读回该组件，再在 `router.js` 引用；不要把所有页面重新包进默认 Shell。根 RouterView 不按 URL 设置 key，避免切换同一布局内的页面时重建整个布局。旧站仍把 Shell 放在 app.js 时，先读回源码，将其移至布局组件、更新路由 children 和 bootstrap 注入，再缩减根组件；重复安装不会自动迁移或覆盖旧站。

## 导航图标

设计系统的选择与安装统一见 `references/Frontend/app-design-systems.md`；组件选择、Shell 与升级方式遵循所选包的指南。

创建时已确定图标，可以通过可选 `create_app_base.navigationIcons` 传入，以 App Plan 导航引用的精确 Screen ID 为键、Lucide kebab-case 名称为值，例如 `{"screen.products":"package"}`。允许只填写部分项目：省略项不写入 `meta.navigationIcon`，可在实现 Shell 时补齐。根据导航用途选择图标，安装器负责写入显式选择，只校验目标 ID 和名称格式，不限制为内置图标集合。缺少图标时的行为遵循所选 Shell 契约。无 App Plan 时省略此映射，在创建业务导航时设置图标。重复安装会保留已有 `router.js`；调整已安装图标时应显式编辑路由 metadata。

## 先完成一个完整可见单元

1. 根据当前授权范围和已有源码确定入口任务。有 App Plan 时选择服务于该任务且有路由的 Screen；保留已有入口，除非审核需求要求改变。无规划时直接实施当前入口任务，不要求页面清单。
2. 阅读已返回的共享用法与当前所需组件/Shell API；仅补读缺失指南。以 props、事件、slots、主题 tokens 和布局契约为准，不从编译 CSS 重建组件。Shell 留白与滚动样式可按所选包指南定位适配样式核对。
3. 自行组合或修改布局时，读取已安装 `layout.default.js` 和 `app.css`，保留 bootstrap、RouterView、路由保护、账户退出和通知能力。保留并扩展该文件已有 setup，而不假设不同 Shell 的内部状态相同。按路由 metadata 组织导航；新增模板变量和处理函数必须从 setup 返回、正确注册或通过有效 Vue 实例属性访问。
4. 仅写入本次需要修改的 `/app.css`、`/layout.default.js`，随后回读各自落库内容。未修改的运行库 Shell 不要求重写。依赖就绪前保留 Route 占位，通过源码检查绑定、导航状态、响应式规则和 RouterView 接入。
5. 按当前已明确的数据策略 实现默认 Screen 的依赖闭包（API → service/store → 必要组件 → 默认 Screen），依赖落库并回读后只替换该 Route 的 PlannedScreen。仍为 PlannedScreen 表示该 Screen 未完成；默认页集成前不开始另一个 Screen。
6. 逐个实施当前授权范围的其余 Screen，再核对整个范围；Shell 完成不代表业务交付。

## 实施中的验证

默认实施使用源码读回、结构检查及 [delivery.md](delivery.md) 规定的有限只读 Preview diagnostics。Shell 源码检查后继续业务实施；浏览器观察不是业务 API、mock API、service/store 或 Screen 的前置条件。

普通实施不得为布局验收主动调用浏览器/iframe 观察、元素查找或检查、导航、点击、设备切换。仅在用户明确要求浏览器测试或操作时使用浏览器工具。读取组件 API 文档不需要打开实际页面。

未实测的运行或视觉行为如实标为未验证。Preview 不可用不阻塞业务实施；保留尚未满足的诊断证据要求，不编造通过。修复源码或返回 diagnostics 中的明确错误，不把 Shell 复核变成反复视觉微调。

## 只补布局，不另造设计系统

- 应用根节点保留 `.app-root`，主内容容器保留 `data-app-region="content"`。底座负责引用 token 的正文字体/颜色、零优先级按钮重置和可收缩主区尺寸，不提供侧栏、页头、栅格、卡片或固定滚动模型。
- 在显示应用名的元素上标记 `data-app-region="identity"`。为完整名称或认可的简称提供足够空间，不能把长名称挤进窄侧栏后接受省略号。窄屏折叠导航可以隐藏名称，但名称必须在可见页头或展开菜单中可读。
- 同一画面只保留一处站点品牌区（名称/logo）。顶栏已经显示品牌时，侧栏从导航内容开始；侧栏承载品牌时，顶栏用于当前页面或操作。响应式布局可以移动品牌位置，但各副本必须互斥显示，展开移动菜单时也不能重复。
- 导航图标可省略；使用时遵循 [设计系统图标规则](../app-design-systems.md)，按所选包公开 API 消费，不用占位符填充空槽位。创建参数 `navigationIcons` 的 Lucide 名称契约仍按上文执行。
- 每个可见的菜单、展开/收起、搜索、账户和通知控件都必须有实际行为。汉堡按钮要在当前断点真正打开/关闭导航；桌面若不支持折叠则隐藏该按钮，支持折叠则同时调整侧栏和主区空间。使用语义按钮及准确的 `aria-expanded`、`aria-controls`，保留键盘和焦点行为。不要放置无处理函数的搜索框或装饰操作入口。
- 账户区域是一个下拉入口：点击用户名/头像展开账户菜单，退出操作放在菜单内部，不能渲染一个无处理函数的用户名按钮再并排摆放“退出”。复用 `accountMenuOpen`、`toggleAccountMenu`、`closeAccountMenu`，让 `aria-expanded` 绑定真实状态，`aria-controls` 指向菜单 ID。菜单支持再次点击、点击外部和 Escape 关闭，关闭后焦点合理返回；与通知面板互斥，导航后关闭。设计包没有 dropdown 时，使用语义按钮和现有 panel/list/button 补足最小局部组合，不凭空假定 `.dropdown` 存在，也不能因为组件缺失省略交互。
- 写入前逐项核对模板与 CSS：图标使用 `<i data-lucide="menu" aria-hidden="true"></i>` 等实际图标或省略；`☰`、`▦` 等字符必须删除。每个展开按钮都要有处理函数、真实状态、目标面板和当前断点的显示规则；仅在 mobile media query 中定义 `.is-open` 时，桌面按钮必须隐藏。读取回来的代码也要复查这些对应关系。
- 退出复用已安装 `/service.auth.js`，使用 `@click="logout()"` 或显式包装处理函数，不能把点击事件作为 URL 参数。真实认证模式执行退出请求及会话清理后通过认证服务的登录 URL 跳转登录页；mock 模式也必须提供登录页跳转，不能静默返回。不得仅关闭账户菜单、回到业务首页或只显示“已退出”；mock 跳转不等于真实会话已注销。
- 写结构前先决定应用名、全局导航和账户控件的归属。若单独的整行顶栏只有右侧账户控件，必须审视其用途：把已有的有用内容合理移入，或把控件整合到其他区域。不要增加装饰搜索、帮助链接、指标来填空。
- 页头只保留必要的品牌/当前位置与紧凑操作组。不要在品牌旁堆放复述业务范围的标语，不把用户名、退出、通知都做成同等强调的按钮；账户入口使用适当的轻量按钮变体。页面标题与副标题表达不同信息，副标题若只是重复 `navigationLabel` 或标题则省略。
- 布局阶段只写当前 Shell 用到的样式，不提前搭建供未来页面使用的通用 `.app-grid-*`、字段行、空状态、抽屉、产品选配组件。账户菜单和通知优先复用匹配的 dropdown/popover/list 组件；加 `.app-` 前缀、引用 token 不能成为重造背景、边框、圆角、字体的理由。确实没有对应组件时，先记录具体缺口，再补局部样式。
- `/app.css` 必须明确父级 grid/flex 与空间分配。flex 主区需要伸展，grid 主区通常使用 `minmax(0, 1fr)`。采用 `.approval-workspace` 等应用专属名称，不假设未定义的通用 `.content` 会自动完成布局。
- 包裹 `RouterView` 的内容容器统一负责页面四周留白，使用运行库文档规定的间距 token，分别处理桌面和窄屏。PlannedScreen 与正式 Screen 共用这层 padding；不得给共享 `.app-planned-screen` 添加 margin 来掩盖布局缺口，也不让各 Screen 重复添加同一圈外侧留白。需要贴边的画布、会话等工作区应明确采用全宽布局，并给内部文字/工具栏保留适当间距，不能因遗漏 padding 意外贴边。
- 选择连贯的滚动模型：自然文档滚动，或有高度边界的工作区；后者需在 flex/grid 祖先链设置 `min-height: 0`，并在实际滚动区设置 `overflow: auto`。不得只加 `overflow: hidden` 把内容裁掉。窄屏要折叠菜单、使用抽屉或上下排列，不能继续让桌面侧栏挤压表单/表格。
- 组件 class 负责字体、背景、边框、圆角、阴影和控件尺寸。先用现有组件和变体，不在 `/app.css` 重造 `.btn`、`.menu-item`、`.table-pagination`、卡片或工具栏。使用 token 的替代外观仍然是重造组件。
- 新业务容器先只写布局属性（display、轨道、gap、padding、对齐、尺寸、overflow）。需要视觉表面时优先复用设计包 card/panel。只有核对组件清单后确实缺失的业务视觉才可新增，并使用局部应用选择器和已有 token。
- 现有组件确需响应式覆盖时，必须限定在应用专属容器下并说明未覆盖的布局需求，不重复原有声明，不全局覆盖组件选择器。
- 自定义语义控件需保留键盘、焦点与原生交互；优先组合运行库公开组件，不修改内部 DOM 或用基础 reset 代替组件契约。
- 不为填充空间添加 KPI 卡片、图表、帮助链接、装饰徽标或重复导航；重要区域必须服务于默认 Screen 的 Blocks/Actions 和主要任务。Shell 与 Screen 不重复显示 App 身份、页标题和菜单。

## 明确的失败条件

手写布局中 `/app.css` 仍只有注释表示布局未完成；已安装运行库 Shell 可以不需要额外 App CSS。两种模式下，业务实施后当前路由仍为 PlannedScreen、应用空白、模板变量未定义、主区不能使用剩余空间或滚动、普通内容意外贴边、品牌重复、符号占位图标、可见控件点击无效果、退出无法到达登录页，或首页偏离主要入口任务，均表示初始化未完成。先修复这些问题，再评价设计区分度或报告完成。
