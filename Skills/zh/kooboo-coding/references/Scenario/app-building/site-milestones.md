# 站点清单（Site Milestone）实施

SiteMilestone 是持久化的交付清单，作为进度记录使用。它不门控任何工具、实施、Preflight 或收口步骤；是否存在 Blueprint/App Plan 也不改变清单的读取和保存方式。规划型 App 的编写仍遵循 [App Plan](app-plan.md)。

## 条目结构

```json
{
  "content": "客户管理：列表、新建、编辑与详情",
  "completed": false
}
```

用 `get_site_info` 读取清单。用 `update_site_milestones` 保存时必须传入完整数组，保存会覆盖已存储的列表。要保留无关条目，就原样包含它们。只有在该交付确实已实施、且你实际执行的验证支持时，才把条目标记为 `completed=true`。

## 选择与排序批次

即使多个相对独立的业务能力会一起实施，也应保持为清单中的独立条目。

轻量 App 与规划型 App 采用相同的范围优先级：

1. 优先遵循用户明确指定的实施范围。实施被点名的模块；当用户明确要求全部模块时，选中并完成整个请求批次，无需再次询问。沿用会话中已确定的范围。
2. 实施已获授权但当前交付范围未指定时，默认选择一个可用的核心业务流程及其必要依赖。简要说明本次交付包含与延后的内容，然后继续；只有当重大业务歧义妨碍选择核心流程时才询问。核心流程可以跨多个模块。仅 Dashboard 本身只有在它交付了用户所需的核心业务结果时才算核心。
3. 全量实施是明确的选项，而不是范围未指定时的默认回退。像"做一个库存系统"这样的宽泛请求、完整的 Blueprint/App Plan 或模块清单，本身不会选中本次交付的全部模块。保留整体范围与剩余条目，但在默认核心批次完成后收口，不自动开始其余部分。

每个批次都要遵循已选定的数据策略。仅规划的请求在规划后结束；范围收窄的修复不授权其他模块。只有在范围未指定时才应用核心默认，绝不用于缩小用户的明确请求，也不用于重建已完成的核心。

## 实施并记录

1. 读取清单和相关的当前规划，确定用户请求的批次。
2. 为已授权的结果创建具体的 Todo。检查实际源码与资源，在编写依赖它的代码前处理真实的依赖。
3. 实施所选能力及所需的共享资源。未来路由保留为明确的占位；每个已实现的路由都需要真实的 Screen 与行为。仅有安装或导航清单不算交付。遵循约定的数据策略；模拟写入不声称已持久化。
4. 运行与改动相称的 Preflight 检查，然后将目标与实际资源和行为逐项对照。部分或未验证的结果，其 Todo 保持未完成。
5. 用 `update_site_milestones` 保存完整清单，只把确实完成的条目标记为 `completed=true`。若运行时证据不可用，记录进度并说明验证待完成。
6. 继续完成剩余的授权工作。保存相关的站点记忆，整理 Todo，然后给出最终总结，分别报告已完成与待完成的条目。

## 运行时验证

Preview 的 `authentication-required`、`loading` 与 `unavailable` 表示运行时验证待完成。不要反复轮询未变化的结果，也不要要求先打开 Preview 才能继续实施。登录页审计不能作为受保护业务页面的证据；登录并返回业务页面后，再收集新的诊断。浏览器操作仍需用户明确选择启用。真实的写入失败、不兼容的依赖、已知的运行时错误和结构性失败仍需修复，不要仅以"待登录"标注。

收口时可以用 `update_planning_topic` 记录已讨论的用户决策，并用 `show_action_button` 展示应用链接。Topic 是讨论记录，不是对 Blueprint/App Plan 的修改，也不构成新的实施授权。收口时不要臆造需求或确认。
