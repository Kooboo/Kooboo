# 内容管理 - 参数配置

## 页面用途

- 后台页面：`/content/useroptions`、`/content/useroptions/create`、`/content/useroptions/setting`、`/content/useroptions/edit`
- 参数配置用于定义一组站点级结构化参数，并维护其实际 JSON 数据。KScript 可通过 `k.paramConfig.{名称}` 读取这组数据。
- 它适合保存业务代码需要读取、但希望由后台人员维护的站点参数。它不是环境变量、服务集成密钥库、内容类型或请求参数校验器。

## 定义与数据是两个层面

- 定义包含稳定名称、后台显示名称和 schema；数据则是按该定义维护的实际 JSON 值。
- “设置”权限用于新建配置和修改显示名称或 schema；“编辑”权限用于修改实际数据。两种权限彼此独立。
- 名称创建后在当前设置页不可修改，并作为 KScript 读取路径的一部分。显示名称只影响后台识别，不改变读取名称。
- 列表点击名称进入数据编辑，设置按钮进入 schema 编辑；修改 schema 和修改数据不是同一个操作。

## Schema 能力

- 字段支持字符串、数字、布尔、对象和数组。
- 数组元素可以是字符串、数字、布尔或对象；对象及对象数组可以继续定义子字段，因此可建立嵌套结构。
- schema 用于生成后台编辑表单，并为 KScript 编辑体验提供结构和类型提示。
- schema 不是运行时数据验证规则。修改 schema 不会自动迁移、转换、删除或补齐已有 JSON 数据，也不会检查旧值是否仍符合新类型。
- 删除 schema 字段后，旧数据中的同名属性可能仍保留在原始 JSON 中；新增字段在表单打开时会按类型使用空字符串、`0`、`false`、空对象或空数组作为初始值。

## 数据编辑与原始 JSON

- 普通编辑界面按 schema 生成输入项，适合维护预期结构中的值。
- 原始 JSON 编辑允许直接调整整个数据对象。当前界面会检查 JSON 是否能解析，但不会验证字段是否存在于 schema、值类型是否匹配，也不会禁止额外字段。
- 保存数据会用当前编辑结果整体覆盖该配置的数据，不是逐字段合并；保存前应确认原始 JSON 中仍保留需要的属性。
- 修改 schema 时，界面虽然会发送一个空数据对象，但定义保存接口不会用它覆盖已有数据；已有数据保持不变。
- 保存成功只证明 JSON 已持久化。业务代码如何解释字段、是否允许空值、以及外部操作是否成功，仍由使用这些参数的 KScript 或页面逻辑决定。

## KScript 读取行为

- KScript 通过配置名称取得已保存的 JSON 值；名称不存在时得到未定义值，而不是自动创建配置。
- 空白数据也会表现为未定义值。业务代码应处理配置缺失、字段缺失和类型与预期不一致的情况。
- 参数配置是站点级共享数据，不按访客、后台用户、语言或请求自动生成不同副本。
- 修改数据后缓存会失效，后续读取使用新值；这不代表已经运行中的外部任务或此前产生的副作用会被撤销。

## 修改与删除风险

- 改变字段名称、类型、嵌套层级或数组元素类型可能使现有数据和调用代码不一致。当前页面不会自动查找或修复这些消费者。
- 删除参数配置会同时移除它的 schema 和数据；引用该名称的 KScript 不会被自动改写，后续读取将得到未定义值。
- 删除前应搜索代码和页面中的读取位置。不要把列表删除确认当作完整的依赖检查或业务回滚。
