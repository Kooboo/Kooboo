# 站点设置 - 角色权限

## 页面用途

- 后台页面：`/system/roles`
- 此页为当前站点定义角色，并按“功能 + 动作”控制 CMS 后台权限。权限是站点级的，不会自动作用到同一组织的其他站点。
- 角色权限不是前台登录、JWT 验证或页面访问规则；这些需要在对应的站点访问和身份验证功能中配置。

## 权限模型

- 每个权限项由具体功能和动作组成。常见动作包括查看、编辑、删除，部分功能还会提供调试或其他专用动作。
- 系统按请求所要求的功能和动作进行精确匹配。勾选某个功能的“查看”不等于自动拥有编辑或删除权限。
- 当前界面在勾选编辑、删除或调试时会同时保留该功能的查看权限；只要这些依赖动作仍被选中，就不能单独取消查看。
- “全选”会改变当前范围内的所有权限。保存前应展开有多项动作的功能逐项复核，避免因为只看功能名称而授予过宽权限。

## 内置角色与自定义角色

- 系统提供 master、developer、contentmanager、member 四个内置角色，并允许创建站点自定义角色。
- 当前界面不允许删除四个内置角色。修改内置角色权限时，会为当前站点保存对应定义，并优先使用该站点定义；这不会改变其他站点的同名内置角色。
- 新角色名称必须唯一，长度最多 50 个字符。角色创建后，当前界面不能直接修改名称；要更名需要新建角色、迁移用户后再删除旧角色。
- 站点或组织所有者会绕过普通角色权限检查，因此不能用所有者账户验证某个受限角色是否配置正确。

## 分配与删除

- 角色保存后不会自动分配给任何用户，需要在“站点用户”页明确选择。
- 已被任一站点用户使用的角色不能删除。删除角色前必须先把所有使用者迁移到其他角色或移除其站点成员关系。
- 删除角色不会自动改写用户、撤销历史操作或迁移到默认角色；系统会直接阻止仍在使用的角色被删除。

## 验证建议

- 权限修改后应使用实际被分配该角色的非所有者账户验证。至少分别测试菜单可见性、列表读取、保存修改和删除操作。
- 菜单隐藏只是前端表现，真正的权限结论应以对应后台请求是否被允许为准；也不要把能打开页面误判为拥有页面内全部动作权限。
