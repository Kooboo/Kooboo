# 服务集成 - OAuth2

## 页面用途

- OAuth2 分组保存微博、Facebook、微信、Google 和 Apple 登录应用的客户端信息，以及授权完成后要执行的回调代码名称。
- 此页不会自动创建登录按钮、登录页面、站点用户、会话或账号绑定逻辑。前台仍需生成 provider 授权地址，并由回调代码决定如何处理用户信息和登录状态。

## 回调地址与域名

- 各 provider 使用当前站点对外基础地址下的固定回调入口，形式为 `/_api/oauth2callback/{Provider}`。必须把页面提示的精确地址登记到 provider 控制台。
- 更换主域名、协议或站点基础地址后，provider 中的回调白名单也要同步更新。多数 provider 要求可公开访问的 HTTPS 地址；仅保存 AppId 和 Secret 不能解决 DNS、证书或回调白名单问题。
- 微信网页登录在 provider 控制台还涉及授权域名；不能把域名登记和完整回调 URL 当成同一项配置。

## 授权与回调代码

- 前台发起授权后，provider 把 code 或 error 返回固定回调入口。系统再使用配置的密钥换取 token 和用户信息，并把结果交给指定的站点回调代码执行。
- 回调代码必须真实存在；名称错误或代码被删除会使授权在回调阶段失败。配置保存不会验证回调代码存在，也不会自动生成它。
- token 和用户资料进入回调代码不等于用户已经登录。创建或查找站点用户、建立 Cookie 或 JWT、处理 state、防止账号误绑定以及决定最终跳转，都属于回调代码的责任。
- `state` 只有在前台发起授权和回调处理都正确校验时才能防止请求混淆；不能只因为 URL 中出现 state 就认定安全校验已经完成。

## 风险与验证

- App Secret、Apple 私钥等属于敏感凭证。修改凭证会影响后续换 token，但不会撤销 provider 已签发的 token 或已经建立的站点会话。
- 验证必须覆盖授权拒绝、code 缺失、token 交换失败、用户资料缺失、回调代码异常、重复回调和最终登录状态。能够打开 provider 授权页不等于 OAuth 登录成功。
